# Project-Wide Agent Guidelines - Version 2 (AGENTS_v2.md)

このドキュメントは、新サブエージェント群が参照する自律開発フロー、エージェントの各ロール（スキル）の責務、およびフェーズごとの連携を定義した共通ガイドライン（テスト運用版）です。新サブエージェントおよび関連タスクは、このポリシーを最優先で遵守して動作します。

特に、本プロジェクトが規定する**「技術憲法（PROJECT_CONSTITUTION.md）」、「情熱とビジョン（VISION_JOURNAL.md）」、「UXストーリー（USER_MANUAL.md §3.2）」、および「GEMINI.md」**に定める全ての遵守基準を、表面上ではなく本質的に満たすための**「3層検証ガバナンス構造」**をここで定義します。

---

## 🗺️ 開発プロセス全体のワークフローと3層検証構造

本プロジェクトは、新エージェント群による戦略策定から実装、メトリクス計測、ゲート判定、異常検知まで、以下の3つの階層による厳格かつ多角的な検証フローを採用します。

```mermaid
graph TD
    subgraph Layer3 [第3層: 意味的・自己改善監査 (Loop Detector & Opus)]
        L3_Check[有効打率 < 10% / メトリクス固着 15バッチ を監視] -->|異常検知| L3_Stop[セッション自動停止 & 自律修復]
    end

    subgraph Layer2 [第2層: 客観的品質ゲート (Orchestrator & Governance)]
        L2_Check[憲法 §20.4 カバレッジ70%以上 / 変更行100% / 負債0 / UXストーリー全PASS を検証] -->|不合格| L2_Block[Phase移行を厳格にブロック]
        L2_Check -->|空PASS3回| L2_Penalty[対象モジュールを3バッチ自動除外]
    end

    subgraph Layer1 [第1層: 自律実行自己検証 (Flash Subagents & Local Val)]
        L1_TDD[TDD 1-Test, 1-Implement 強制] --> L1_Val[ローカルテスト & カバレッジ確認]
        L1_Val -->|変更なし| L1_Skip[ステータスを skip として自律申告]
    end

    Layer1 --> Layer2 --> Layer3
```

## 👥 各ロール（スキル）の役割と検証責任

各ロールは、割り当てられたタスクの実行において、憲法・ビジョン・UXストーリーの遵守責任を負います。

| ロール（スキル名） | 責務概要 | 成果物と配置パス | 遵守・検証責任 |
| :--- | :--- | :--- | :--- |
| **Product Owner**<br>(Opus / Strategist) | 全体の進捗監視、Directiveの策定。相反（コンフリクト）の決定。 | `backend/agents/orchestration/opus_directive.json` | 憲法 §26 に基づく**自己改善サイクルの統括**。スタグネーション検知時のDirective自律更新。 |
| **Task Executor**<br>(Flash Subagents) | `test_weaver`, `bug_hunter`, `refactor`, `thumbnail` などの各タスクを実行する。 | 各実装ファイル・テストコード | `GEMINI.md` の**TDDプロトコルの順守**。実装前のRedテスト作成と変更対象行カバレッジ100%の保証。 |
| **Metrics Collector** | バッチ実行完了後、動的にテスト（pytest）やカバレッジを測定・収集し反映する。 | `backend/agents/memory/phase_state.json` の `metrics` 部 | `coverage.json` およびテスト一覧の**改ざんのない客観的収集**。 |
| **Gate Keeper** | 現在のメトリクスが次のPhaseの移行条件（Phase Gate）を満たしているか検証する。 | `backend/agents/memory/phase_state.json` の `current_phase` | 憲法 §20.4 の**品質ゲート基準**（カバレッジ・負債）および **UXラチェット（O-1〜O-12, A-1〜A-7）** の厳密検証。 |
| **Loop Detector** | 有効打率の低下（空振り）、重複ループ、メトリクスの固着などの異常を検知する。 | `backend/agents/orchestration/flash_session.json` の自動停止 | 無駄打ち・空振りの**機械的検知と物理的ペナルティの適用**（3バッチ自動除外、自動停止）。 |

## ⚙️ フェーズ間ガバナンスと協調のお約束

### 1. 意思決定プロセスと相反（コンフリクト）の解消
- **最終決定権**: 指摘対応やタスクの優先度に複数の選択肢がある場合、あるいはリソース競合が生じた場合は、Product Owner（Opus）が優先決定権を持ちます。
- **指示の順守**: Flashエージェントは、`opus_directive.json` に記載された優先順位およびポリシーに厳密に従ってタスクを選択しなければなりません。

### 2. 未済管理（チケット・ステータス管理）の仕組み
- **空PASSペナルティ (Anti-Stagnation)**: `changed_files: []` (変更なし) で完了したタスク（空PASS）は `skip` とし、同一モジュールへのタスクが3回連続して空PASSとなった場合、そのモジュールは3バッチの間自動的にブラックリスト化（一時除外）され、タスク生成から除外されます。
- **ブラックリストの棚卸し**: 蓄積されたブラックリストは、Product Ownerがレビューし、定期的に自動リセットまたは解除の判断を行います。

### 3. ソースコード変更時のローカルバリデーション（第1層）
- **非退行の保証**: コードを変更したエージェントは、コミットまたはバッチ完了報告を行う前に、必ずローカルで以下のバリデーションを実行し、すべて成功していることを実証しなければなりません。
  - 静的解析およびテストの実行 (`pytest -q`)
  - **変更対象行カバレッジ 100%** の検証・保証

### 4. 異常検知と自動エスカレーション・自律修復（第3層）
- **自動セッション停止 (Stagnation Auto-Stop)**: 以下の異常を検知した場合、システムは即座にセッションを停止 (`auto_stop`) し、ユーザーまたはOpusへエスカレーションを通知します。
  - **メトリクスの固着**: 15バッチ連続でテスト数やカバレッジに一切の変動がない場合。
  - **有効打率の急低下**: 直近3バッチの有効打率（実質変更あり比率）が 10% を下回った場合。
  - **重複無限ループ**: 同一モジュールへのタスクが異常な頻度で繰り返し生成された場合。
- **自律修復 (Self-Healing & Adaptation)**: 異常を検知してセッションを停止した際、Product Owner (Opus) は `opus_directive.json` のブラックリストおよび優先度を自律的に更新し、開発ループが停滞から自律復旧できるように支援します。
