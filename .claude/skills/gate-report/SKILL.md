# ゲート報告

human-on-the-loop の**唯一の判断点**。ここでユーザーが見るものが判断材料の全部。

## 原則

**主張ではなく証拠を出す。** 「テストが通りました」ではなく、走らせたコマンドと
その出力、CI の run ID を出す。レビューは再実行より速くなければ意味がない。

**自分の成果を自分で採点しない。** 終了条件の充足判定は `gate-verifier`
サブエージェントに別コンテキストで検証させ、その結果を載せる。

## 構成（この順で、これ以上は書かない）

### 1. 判断してほしいこと（1行）

> 次フェーズ `<id> <title>` に進んでよいか。

### 2. 終了条件の充足

| 条件 | 判定 | 証拠 |
|---|:---:|---|
| C-1 … | ✅ | `pytest ...` 3,637 passed / CI run 30722167524 |
| C-2 … | ⚠️ | 測れていない。理由: … |

`gate-verifier` が反証できなかったものだけ ✅。**反証を試していない条件は ✅ にしない。**

### 3. スコアの変化

前回 → 今回、軸ごとの増減。下がった軸があれば必ず理由を書く。

### 4. このフェーズで入れた変更

PR 番号と1行要約だけ。詳細は PR 本文にある。

### 5. 想定と違ったこと

計画時の前提が外れた点。**次フェーズの定義に影響するのはここ**なので省略しない。
何も無ければ「なし」と書く。

### 6. 次フェーズの提案

正典の `axis_scores` から「重み × 改善余地」が最大の軸。
**提案であって決定ではない。** フェーズの定義はユーザーの領分。

### 7. 積み残し

このフェーズの条件に紐づかず、見つけたが手を付けなかったもの。
バックログの ID で。

## 出したあと

**次フェーズには入らない。** ユーザーの判断を待つ。
待っている間に着手してよいのは、CI の追随（`gh pr update-branch`）と
このフェーズの PR のマージ完遂まで。
