## 採点の規則（今回当てたもの）

正典の `scoring_policy` の段をそのまま使った。

| 証拠の段 | 点 |
|---|---|
| コード存在 | 最大 20 |
| テスト通過（CI で失敗0） | 最大 40 |
| 静的検証 + CI ゲート | 最大 50 |
| E2E 動作確認 | 50 から。**動いた割合**で上積み（`pipeline_e2e` は 50 + 50 × 6/11 = 77） |
| 表示の E2E（画面が実データの API で描ける） | 50〜75。API の成功率で配分（`ui_api_connection` は 50 + 25 × 11/12 = 73） |
| 操作の E2E（画面から走らせて完成まで）・本番動画での確認 | 75〜100。**今回は測っていない** |

- **動作は確かめたが目的を果たしていないものは、E2E の下限 50 で止めた**（`quality_auto_improve`: 回るが改善しない）
- **実走での観測が逆向きのものは、上積みしない**（`soul_auto_evolution`: 学習が記憶を消した）
- **E2E で確かめた項目が一部だけの軸は、軸として静的検証の段にとどめた**（`ux_guarantee_owner`: 12項目のうち3）

**この規則は私が決めて当てたもの**で、採点方針の段の間をどう配分するかは方針に書かれていない。
**自分の成果（R1.5）を含む軸を自分で採点している**ので、規則か点に異論があれば直す。

## 手法についての記録

- **キャッシュ依存の成功を根拠にしない**（2026-04-18 の前例）。今回も同じ日の先の2本はキャッシュ込みだった
- **画面を見るだけのときはダミーキーで起動する。** 課金の経路を塞いだうえで、通信が GET だけだったことも確かめた
- **監査の実走の副作用はコミットしない。** 実行時に書き換わる追跡ファイルは戻し、費用の台帳だけ残す
- **方針の天井を当てて下げたものと、実測で下げたものを分けて書く。** 読む人が「退行した」と誤読しないように
