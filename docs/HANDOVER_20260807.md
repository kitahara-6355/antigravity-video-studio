## 3. この作業で効いた原則（次も効く）

**`gate-verifier` は P2 で3回、P3 で2回、計5回とも当たった。** 通さずに
「完了」と報告していたら5回とも偽の緑を出していた。**必ず通す。**

指摘はすべて同じ型だった: **走査範囲の外にポケットが残る。**

| 回 | どこにポケットがあったか |
|---|---|
| 1 | 89件の endpoint 判定のうち 37件はレスポンス本体の主張なのに経路の実在しか見ていない |
| 2 | まだ6件が未宣言。`_render_settings.copy()` を走査が展開できていない |
| 3 | ラチェットが verdict しか比較せず、宣言を消すだけで全部が無検出で巻き戻る |
| 4 | **監査自身の走査範囲が実行系より狭く**、その隙間の項目が3ゲートすべてをすり抜ける |
| 5 | **`claim` は人手で貼るラベルで、description との対応を誰も検証していない。** 弱いラベルを選ぶ・宣言を緩いものに差し替える、で 3ゲート緑のまま FAIL→PASS を作れる |

**5回目で分かったこと: 「対応が取れている」は自己言及だった。** 監査が突き合わせて
いたのは「`claim` 種別 ↔ 宣言」だけで、その `claim` 種別が description を
言い当てているかは誰も見ていない。`description` が `success=true` の項目に
`claim: response_field`（＝値は見ない、と自分で明記している）を貼れば、
主張の半分を捨てたまま緑になる。**ラベルを人が貼る限り、ラベルの妥当性を
機械で見る層がもう1枚要る。**

**閾値を終了条件にしない。** P2 の C-2「充足率 90% 以上」は数え方に依存する値
だったため、検証のたびに数字が動いた（68.0% → 89.34% → 86.07%）。**同じ実装の
まま、数え方だけで 68% にも 89% にもなる。** P3 は「対応が取れていない項目が
ゼロ」を条件にして、この振動を止めた。

**判定していないものを PASS にしない。** 判定手段が無いなら `unjudgeable` の
FAIL として理由つきで出す。数字は下がるが、下がった数字は本当のこと。
