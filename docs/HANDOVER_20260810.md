### 判定の4層（ここが設計の核）

1. **SCANNED** — 構文で開く形（`fetch` / `new WebSocket` / URL 属性 / `window.open`）
2. **UNSCANNED** — 正規表現で検出する形（axios・location 遷移・`fetch.call` など20種）
3. **残余 `unattributed`** — 1・2 のどれにも紐づかない backend URL リテラル
4. **`comment_masked`** — コメント除去の前後で検出結果が変わったもの

1・2 は数え上げなので必ず漏れる。**3 が 1・2 の補集合を受け、4 が 3 の前提
（コメント除去が正しいこと）が崩れた場合を受ける。** 層を足すたびに
「その層の前提が崩れたら？」が次の穴になったので、最後は前提の崩壊そのものを
検出対象にした。

## 4. この作業で効いた原則（次も効く）

**`gate-verifier` は14回中14回当てた。** 毎回、実測の反例つき。通さずに
「完了」と報告していたら14回とも偽の緑を出していた。**必ず通す。**
呼ぶときは「実在の反例が無いのに not_met に倒さないこと」を明記する
（そう書いてからも14回目まで反例が出続けた＝正当だった）。

### 私が原因の穴が7件あった。2型しかない

1. **修正が新しい沈黙を作った（5件）**
   6回目=生テキスト検出／7回目=正規表現誤読／9回目=fail-safe／10回目=`}`／
   12回目=未適用。**閉包を広げる実装自体が新しい沈黙を作る。**
2. **報告と実態の食い違い（2件）**
   10回目=自己チェックが不十分（試した形が狭かった）／
   12回目=置換が無言で失敗したのに差分を見ずに「入れた」と報告

**対策（次も守る）:**
- **コードを変えたら `grep` で実在を確認してからコミットする。**
  ヒアドキュメントの置換は無言で失敗する。`Edit` ツールを使うか、
  適用後に必ず `grep -n` で行番号を出す
- **「自分で試して問題なし」は証拠にならない。** 試した範囲を明記する
  （「4パターン試した」ではなく「この4パターンだけ試した」）
- **その場しのぎの安全弁を足さない。** 9回目の fail-safe は10回目の穴になった。
  判定が怪しいなら判定そのものを直す

### 閉包の作り方

- **数え上げは必ず漏れる。補集合を受ける「残余」を必ず置く。**
  6回目に `unattributed` を入れたら、形を1つも足さずに5形が捕まった
- **層の前提が崩れた場合も検出対象にする。** 11回目の `comment_masked` は
  「コメント除去が正しい」という前提の崩壊を受ける層
- **fail-open を作らない。** 「読めなかった」を「問題なし」に混ぜない。
  メソッドだけ既定値を主張する、のような非対称な手抜きが2回穴になった
- **ハードコードした前提が宣言と食い違う。** `/api` 決め打ちで、実在する
  `/health` `/ws/*` `/themes/*` `/soul/*` の25パスが見えていなかった。
  **判定基準は宣言側から導く**
