# UX 検証 L1 の切り分け（2026-08-02）

Phase 1 の終了条件 C-5「既存 FAIL 16件（O-1 に14 / O-8 に2）が実在の不具合か
古い判定かを切り分ける」に対する回答。

**結論を先に書く。実在の不具合として確認できたものは 0 件。**
16件は「不具合が確認された」のではなく「**判定が古く、対象もずれている**」。
うち1件は現在では明確に PASS であり、2件は逆に「PASS のはずがないものが
PASS になっていた」。

---

## 1. FAIL 16件はどこから来ているか

正体は `backend/tests/e2e_results.json` である。`gap_analyzer.py` がこれを
読み、ストーリー定義と突き合わせて PASS/FAIL/SKIP を出す。
`snapshots/v8_baseline.json`（2026-06-28）の 16 FAIL はその出力。

このファイルは **初回コミット `bb1bcde` 以降1度も更新されていない。**

```
$ git log --oneline -- backend/tests/e2e_results.json
bb1bcde 初回コミット: AI動画生成パイプライン
```

## 2. このファイルはストーリー定義と同期していない

`e2e_results.json` には **FAIL が 31件** 記録されている。しかし
**そのうち 15件は、現在のストーリーに存在しない項目 ID** を指している。

| 消滅した項目 ID | 記録先 |
|---|---|
| O1-L1-08 / 09 / 10 / 11 | `dom_checks` |
| O1-L2-08 / 09 / 10 / 11 | `visual_checks` |
| O1-L3-09 / 10 / 11 / 12 | `interaction_checks` |
| O1-L4-07 / 08 / 09 | `state_checks` |

`gap_analyzer` は現存する項目しか集計しないので、31 − 15 = **16** が
v8_baseline に出ていた。O-1 が 14、O-8 が 2 で内訳も一致する。

**つまり「16」という数字自体が、消滅した項目を落とした残りかすである。**
この判定結果を現在地の根拠にはできない。

## 3. L1 の6件を新しい実行系で判定し直した

Phase 1 C-1 で入れた実行系（`backend/ux_verification/executor.py`）で、
L1 の 24項目を旧判定と突き合わせた。**21件は一致、3件が食い違う。**

| 項目 | 旧(e2e) | 新(静的走査) | 何が起きているか |
|---|---|---|---|
| O1-L1-01 | FAIL | **PASS** | `data-testid="video-file-browser"` は `ProductionPipeline.jsx:459` に実在する。**旧 FAIL は古い** |
| O1-L1-04 | PASS | **FAIL** | `extension-filter` という DOM 要素は存在しない |
| O1-L1-06 | PASS | **FAIL** | `validation-api` という DOM 要素は存在しない |

食い違いの3件はいずれも同じ原因に行き着く。

## 4. 根本原因 — 宣言された検証方法と、実際に測っていたものが違う

O-1 と O-8 の L1 項目の説明文を読むと、DOM の主張ではない。

```
O1-L1-01  動画一覧APIが正常応答を返す          test_method: dom_exists
O1-L1-03  メタデータAPIが必須フィールドを返す   test_method: dom_exists
O1-L1-06  バリデーションAPIが正常応答を返す     test_method: dom_exists
O1-L1-07  localStorageに履歴キーが存在する      test_method: dom_exists
O8-L1-01  ヘルスチェックAPIが正常応答           test_method: dom_exists
```

`validation-api` や `recent-history` は **DOM 要素の名前ではない**。
旧ハーネスは `dom_exists` というラベルのもとで **API の応答**を測っていた。
だから O1-L1-04 / O1-L1-06 は PASS になり、静的走査では FAIL になる。
**同じ項目に対して、両者は別の問いに答えている。**

これは O-1 / O-8 に限らない。Owner の L1 122項目のうち、
**86件が testid を持たず、その 78件は API・データ契約の主張**である
（「statusフィールドが存在する」「evolution_entries含む」など）。

## 5. 16件の最終的な切り分け

| 区分 | 件数 | 内訳 |
|---|---|---|
| **古い判定であることが確認できた** | 1 | O1-L1-01（現在は PASS） |
| **判定は維持されるが、理由が特定できた** | 5 | O1-L1-02 / 03 / 07（要素が無い）、O8-L1-01 / 02（testid 未定義） |
| **未検証。不具合とは言えない** | 10 | O-1 の L2〜L5（本フェーズのスコープ外） |
| **実在の不具合として確認できた** | **0** | — |

加えて、旧判定で **PASS になっていた 2件（O1-L1-04 / O1-L1-06）が、
宣言された検証方法では PASS を主張できない**ことが分かった。
切り分けの結果は「FAIL が減った」ではなく「**PASS も FAIL も、
測っていた対象が違った**」である。

## 6. 残る 10件を今すぐ判定できない理由

L2〜L5 は動作中のバックエンドを要求する。`backend/.env` が無く実 API キーが
未設定のため、そもそも実行できない（D-20）。**Phase 1 のスコープ外**として
据え置く。据え置きであって「PASS」でも「不具合なし」でもない。

## 7. 推奨（判断はユーザーの領分）

1. **`backend/tests/e2e_results.json` を現在地の根拠から外す。**
   初回コミット以降更新されておらず、FAIL の半数が消滅済み項目を指している。
   `snapshots/quarantined/` と同じ扱いにするのが一貫する。
   **削除は提案しない** — 唯一の過去記録なので、隔離して由来を残す方がよい。
2. **L1 の 78件は `dom_exists` では判定できない。** API・データ契約の主張を
   DOM 存在確認で測ることはできない。取りうる道は2つあり、どちらもフェーズの
   定義に関わるのでゲートで判断を仰ぐ:
   - (a) API 契約を静的に判定する実行系を別に作る（無料・CI 可）
   - (b) ストーリー側の `test_method` を実態に合わせて訂正する
     （ただし項目の削除はラチェット違反）
3. **`docs/ux_fulfillment_matrix.md` と同様、v8_baseline も現在地に使わない。**
   2026-06-28 の値であり、上記のとおり内訳が壊れている。
