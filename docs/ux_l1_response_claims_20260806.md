# レスポンス内容の主張を判定する（2026-08-06）

P2 の終了条件 **C-2** に対する、`gate-verifier` の指摘への回答。

**指摘。** endpoint で判定していた 89 項目は 47 個のエンドポイントにしか対応して
おらず、そのうち 37 件は「statusフィールドが存在する」のような**レスポンス内容の
主張**なのに、判定しているのはエンドポイントの実在だけだった。この 37 件を
「主張が検証されていない」として除くと 83/122 = **68.0%** で 90% を割る。
つまり閾値の充足がこの 37 件に依存していた。

**対応。** 判定手段を足した。指摘は正しく、P1 で解消したはずの
「dom_exists のラベルで API を測る」偽 PASS が、経路の粒度に移っていただけだった。

```bash
python -m backend.ux_verification.executor --persona owner
```

| | 前 | 後 |
|---|---:|---:|
| PASS | 120 | **112** |
| うち内容まで判定 (`field_found`) | 0 | **25** |
| FAIL | 2 | **10** |
| 充足率 | 98.36% | **91.80%** |

**数字は下がったが、判定されていない主張は 37 件から 8 件に減った。**
しかもその 8 件は PASS のままではなく FAIL として出ている。
`gate-verifier` の厳しい数え方（主張が検証されていないものを PASS から外す）でも
112/122 = 91.80% で、C-2 の 90% を満たす。

---

## 1. 何を見るようにしたか

`response_field` を宣言した項目は、ハンドラの返り値にそのフィールドが現れるかまで
判定する。現れなければ `field_not_found` で FAIL。

ルーターの `return` を読むだけでは足りなかった。実測すると本番のハンドラは
ほとんどが薄い受け皿で、中身はサービス層が組み立てている:

```python
# backend/routers/trinity.py:158
status = service.get_evolution_status()
return status                       # ← ここだけ見ても 0 フィールド
```

そこで (1) ハンドラ内のローカル代入を辿り、(2) 呼び先の関数を `backend/` 全体の
索引から引いて**一段だけ**展開する。結果は
`recommendation.recommended_segments.score` のようなドット区切りのパスで持ち、
**どこで見つけたかを証拠に書く**:

```
static_response_scan: routers/smartcut.py:189 POST /api/smartcut/recommend
  が recommendation.recommended_segments.score を返す
```

一段しか辿らないのは、辿り始めると呼び出しグラフ全体になり、
「どこで見つけたのか」を証拠として書けなくなるため。索引の構築は約 4 秒。

## 2. ラチェットとの関係 — 「厳しくした」を機械で区別する

判定を厳しくすると PASS が減る。実装の退行と見分けが付かない。
かといって「厳しくしたから」で何でも通せるようにすると、ラチェットが機能しない。

そこで `--tighten` を足した。**受け入れるのは新しい判定理由が `field_not_found` の
ものだけ**で、`not_found`（実体が消えた）や `unregistered`（登録が外れた）や
項目の削除が混じっていれば拒否する。理由は必須で、ベースラインに履歴として残る:

```json
"tightenings": [
  { "reason": "レスポンス内容の主張を…判定するようにした（P2 C-2）",
    "items": ["O11-L1-10", "O12-L1-07", ...] }
]
```

履歴を消さないのは、消すと「昔は緑だった」が見えなくなり、退行と区別が
付かなくなるため。`--tighten` を使わなければ、同じ差分は普通に違反として止まる。

## 3. 残る 8 件の切り分け

**実在の欠落は 0 件。** 5 件は照合先の書き方が実装と食い違っており、
3 件は静的走査では原理的に判定できない。

### 3.1 仕様の穴 — 機能は実在。照合先が違う（5件）

| 項目 | 主張 | 宣言された照合先 | 実体 |
|---|---|---|---|
| O11-L1-10 | `hook_score` 含む | `POST /api/youtube/pre-plan` | **`POST /api/youtube/optimize`** が返す（`youtube_optimizer.py:629`） |
| O12-L1-07 | `user_model` オブジェクト含む | `GET /api/evolution/status` | **`GET /status`** が `branding_manager.user_model` を丸ごと返す（`trinity.py:53`）。レスポンス**そのもの**であってフィールドではない |
| O12-L1-08 | `result` 含む | `POST /api/analytics/sync` | レスポンス自体が result（`biz_xp` / `quests` / `rivals` / `stats`）。**`result` は変数名であってフィールド名ではない** |
| O6-L1-05 | 4カテゴリ(audio/video/subtitle/structure)が存在する | `GET /api/pipeline/quality-gate/scores` | `categories[].id` の**値**。フィールド名ではない（拾えるのは `categories.id` / `categories.name` / `categories.score` …） |
| O8-L1-10 | `output_file` 存在 | `GET /api/render/status/{job_id}` | **`POST /api/render/complete/{job_id}`** が返す（`render.py:315`）。status 側は `stages` / `progress` / `current_stage` などを返す |

いずれも**実装は在る。** 直すべきはストーリー側の照合先だが、
これは仕様の書き換えなので実行しない（C-4 と同じ扱い。§5 参照）。

### 3.2 判定不能 — 静的走査の原理的限界（3件）

| 項目 | 主張 | なぜ判定できないか |
|---|---|---|
| O12-L1-10 | `entries` 配列含む | `GET /api/evolution` は `branding_manager.get_evolution_log()` = `self._load_json(path)` を返す。**レスポンスの形はディスク上のデータが決めており、コードには書かれていない** |
| O4-L1-11 | 候補に `type` フィールドが存在する | `get_all_candidates()` は `{"highlights": self._context.all_highlights, ...}` を返す。**要素の型は実行時のオブジェクトで、静的には追えない** |
| O4-L1-12 | 候補に `timestamp` フィールドが存在する | 同上 |

**これらを PASS にする方法はある——`response_field` を書かなければよい。**
書かなければ経路の実在だけで PASS になる。それをしないのは、
判定していないものを緑にするのが今回潰した偽 PASS そのものだから。

## 4. 判定の限界（新しく増えた分）

`api_contract.py` の既存の限界に加えて:

- **呼び先は一段しか辿らない。** サービスがさらに別のサービスを呼んで組み立てて
  いる場合は見えない
- **呼び先は関数名だけで引く。** 同名の関数が複数あれば**和集合**になり、
  偽 PASS 側に倒れる。厳密な解決には import の追跡が要り、静的走査の範囲を超える。
  そのため証拠にはパスを残し、どこで当たったかを追えるようにしてある
- **末端の名前でも一致させる。** ストーリーの多くは位置を書いておらず
  「レスポンスのどこかに在る」ことまでしか主張していないため。
  位置まで主張したい項目は `recommendation.score` のようにドットで書けば
  完全一致で判定される
- **同じ変数に複数回代入していたら最初の1つだけを使う。** どれが返るかは
  静的には決まらないので、後の代入で「見つかったことにする」のを避けた

## 5. ユーザーの判断を仰ぐこと

§3.1 の 5 件は**照合先を実体に合わせれば PASS になる**（充足率 91.80% → 95.90%）。
ただしこれは仕様の書き換えなので、実行前に承認が要る。
P2 で O-1 の 5 件に同じことをしたとき（PR #52）も同じ手順を踏んだ。

**`test_method` と説明文は書き換えない。** 項目の削除も起きないのでラチェットには
抵触しないが、**誤った仕様を消す**操作であることは変わらない。

§3.2 の 3 件は、静的走査では判定手段が無い。実行時の応答を見る層（L2 以降）が
要るが、それは `backend/.env` が無いため現状そもそも実行できない（D-20）。
