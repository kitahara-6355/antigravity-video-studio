# L1 の判定が何を保証するか（2026-08-06 決定）

P3 の C-3 に対する `gate-verifier` の4回目の指摘への回答であり、
**ユーザー判断の記録**でもある。

## 指摘

> `route_exists` と分類された 47件は**全件が description で「正常応答を返す／
> 正常応答する」と主張している**。判定は経路の実在＋ルータ登録だけ。
> 同じ述語を持つ O4-L1-05「4種プリセットで API が正常応答する」は
> `runtime_behavior` として FAIL にしており、**同一の主張が 47件は PASS、
> 1件は判定不能という一貫しない分類**になっている。

指摘は正しい。分類が一貫していなかった。

## 決定 — (A) L1 の「正常応答」は経路の実在と読む

ユーザー判断（2026-08-06）。選択肢は2つ提示した。

| | 読み方 | 充足率 |
|---|---|---:|
| **(A)** | L1 の「正常応答」は「経路が実在し、アプリに登録されている」。実際の応答は L2 の担当 | **89.34%**（据え置き） |
| (B) | 「正常応答」は 200 が返ること。静的には判定できないので 47件すべて FAIL | 50.82% |

**(A) を採用。** 根拠は、L1 は静的・L2 以降が実行時、という層構造がこの
プロジェクト自身の設計であること。`executor` の出力冒頭も
「※ いずれも静的走査。実行時に描画される / 200 を返すことは保証しない」と
最初から明記している。

**ただし (A) は「曖昧なままにしてよい」という意味ではない。**
何を確かめ、何を確かめないかを書かずに 47件を PASS にしておくのは、
P3 が潰そうとしている置き換えそのもの。そこで2つ手を打った。

## 1. 判定の意味を機械可読にした

`CLAIM_SEMANTICS` に、claim ごとの「確かめること」と**「確かめないこと」**を
書いた。テストで、claim を足したのに意味を書き忘れることを禁じている。

```bash
python -m backend.ux_verification.claim_audit --semantics
```

`route_exists` の欄はこうなっている:

> **確かめる**: そのエンドポイントが定義され、アプリに include_router されている
> **確かめない**: **呼んで 200 が返るか。** ハンドラが例外を投げるかは静的には
> 分からない。L1 が保証するのは『呼び先が存在し、404 にはならない』ところまで

分類だけして意味を書かないと、「正常応答を返す」を経路の実在で PASS に
しているのが妥当かどうかを読み手が判断できない。

## 2. O4-L1-05 を分類し直した

`runtime_behavior` → **`parameter_coverage`**。

判定できないのは「正常応答」の部分ではなく、**「4種プリセット(15/30/45/60分)で」
という入力値の集合**のほう。`RecommendRequest.target_duration_minutes` は
`int` としか書かれておらず（`smartcut.py:51`）、受理する値の集合が実装のどこにも
宣言されていない。15/30/45/60 という数はハンドラの docstring とコメントにしか
現れず、**静的走査には照合する相手が無い。**

これで「同じ述語なのに扱いが違う」は解消した。47件と O4-L1-05 の差は
述語ではなく、**入力値の集合を主張しているかどうか**にある。

## 判定不能の4種類（確定）

| claim | 件数 | 確かめられない理由 |
|---|---:|---|
| `element_count` | 1 | 描画される件数。既定データの件数なら静的に数えられるが、主張は「表示される」で実際の描画件数は実行時のデータ次第。既定データで代用するのは別の主張への置き換え |
| `idempotency` | 2 | 2回呼んで同じ結果になるか |
| `parameter_coverage` | 1 | 受理する値の集合が実装のどこにも宣言されていない |
| `spec_incomplete` | 1 | 何を照合すべきかが仕様に書かれていない |

いずれも `unjudgeable` の FAIL として理由つきで出る。**PASS には逃がさない。**

### `element_count` について補足

`gate-verifier` は「既定セグメントは静的定数（`pipeline_default_states.py:170`）で
3件以上あるので『原理的に判定できない』が確立していない」と指摘した。
事実として定数は 3 件ある。

それでも判定不能としたのは、**主張が「表示される」だから**。
既定データは「まだ何も文字起こししていないときに API が返す値」であって、
実運用で画面に出る件数ではない。定数の長さで代用すれば
「既定データが3件以上ある」という**別の主張**を判定したことになる。

## この決定が変えないこと

- 充足率は 122件 / PASS 109 / FAIL 13 / SKIP 0 = **89.34%** のまま
- **P3 は充足率を終了条件にしていない**（`design_note`）。条件は
  「主張と判定手段の対応が取れていない項目がゼロ」
- 47件の PASS は「呼び先が存在し 404 にならない」ことの保証であって、
  「200 が返る」ことの保証ではない。**L2 が要る**（`backend/.env` が無いため
  現状は実行できない — D-20）
