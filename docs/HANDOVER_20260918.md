## 3. C4b の門 — 面と鍵をまるごとラチェットする（2026-09-17 ユーザー承認）

**なぜこの形か。** 25周目の診断は「判定を静的述語から観測へ移しても、母集団の定義が
**意味**で書かれている限り無限性は残る」。3周期とも同じ形だった:

|---|---|---|
| 〜20 | どの site か | 台帳（limits #17） |

**述語を無くした。** 検出は機械的、意味の判断は査読（台帳への記入）にだけ残る。

- **面** = 出力口＋入力条件。`/api` の GET 404 ルート × 条件6（既定・実走後の採点済み（合格）・
  採点済み（不合格）・未採点・品質改善ループ（不合格）・品質改善ループ（未採点））＋サイドカーの分岐5 = **2,429 面**。
  条件つきの面は、既定の面の形からはみ出すものだけ台帳に載せる（台帳は 429 面）
- **パス引数**: 合成の値（`c4-gate-probe`）と、台帳 `path_values` で対応づけた一覧 API が返す値
  （26周目にユーザー承認で条文を広げた）。テンプレート付きの GET は全部、`from`/`take`/`limit`・
  `values`・`none`（理由つき）のどれかを書く。書いていない・一覧から値が取れない・使われていない宣言は FAIL
- **実走後の条件は本番に作らせる**: 結果は `_build_result`、採点は本番の `QualityGateWorker`
  （物理検査と減点の合計だけ差し替え。採点結果の形は本番の `run_all_plugins` を1度走らせて借りる）、
  工程の状態は本番の配線（coordinator `_notify_result` → router `_update_stage`）。
  未採点は coordinator の `_normalized(worker, None)`（結果を返さなかった工程）。
  **改善ループの条件はさらに `_notify_retry` まで進める**（27周目 E1。畳むと上書きで前の状態が見えない）
- **点数の差分**: 条件ごとに点数だけを変えた2回（甲・乙）と、甲をもう一度（甲2・揺れの除去）。
  点は**表示の閾値をまたぐ**ように選ぶ（合格 92/97・不合格 85/79・未採点 0/97.3。品質ゲートの90点はまたがない）。

- **FAIL**: 新しい鍵・新しい面・消えた面・出口（status と種類）の変化・**出所の印の消失**・分類されていない鍵名・
