## はじめに
本仕様書は、Antigravity2.0環境において、開発スピードを極限まで高めつつ品質と安全性を保証するための、**サブエージェント並列処理**および**24時間継続稼働**に関する恒久的なワークフローとベストプラクティスを定義する。

デュアルモデル構成（Gemini 3.5 Flashによる超並列実行と、Claude 4.6 Opusによる高知能監査）を安全かつ効率的に駆動するための具体的な技術要件と運用手順を示す。

## 第1章: サブエージェント並列実行の極意 (I/O・テスト競合回避)

最大30並列のサブエージェントが同時にファイル編集、テスト実行、依存関係の解決を行う際、競合によるハングやテストの誤検出を防ぐため、以下の分離ポリシーを徹底する。

### 1.1 ワークスペースの物理的分離 (Workspace Mode: share/branch)
- **原則**: サブエージェントを起動する際は、親エージェントと同一のフォルダを直接共有せず、`Workspace: share` または `Workspace: branch` を指定する。
  - `share`（git worktree同等）: ディスクスペースを節約しつつ、個別のブランチおよびワーキングツリーを割り当てる。
  - `branch` (クローン): 完全な分離が必要な場合に使用する。
- **一時ファイルの隔離**:
  各エージェントは、プロジェクトルート直下の `temp/` や `scratch/` をそのまま使わず、必ずエージェントの会話ID（`conversation_id`）に紐づいた隔離フォルダ（例: `temp/{conversation_id}/`）を作成して使用する。

### 1.2 テストDBおよびキャッシュのネームスペース分離
- **テスト用データベース**:
  SQLiteなどのデータベースを使用するテストでは、ファイル名にエージェントIDまたはスレッドIDを動的に付与する。
  - 例: `test_db_{agent_id}.db`
  - 実装方法: テストスイートの `conftest.py` 内で、環境変数 `ANTIGRAVITY_AGENT_ID` を読み込み、接続文字列を動的にオーバーライドする。
- **pytest キャッシュの競合回避**:
  並列で `pytest` を実行すると、`.pytest_cache` のロック競合が発生する。以下のオプションを付与してキャッシュディレクトリを個別に指定する。
  ```bash
  pytest -o cache_dir=.pytest_cache_{agent_id} tests/
  ```

### 1.3 ポートの動的割り当て
- FastAPIやViteなどのサーバーを並列テストで起動する際、デフォルトポート（`8000`, `5173` 等）の衝突を避けるため、空きポートを動的に探索するユーティリティを介してポートを決定する。
  ```python
  import socket
  def get_free_port():
      s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
      s.bind(('', 0))
      port = s.getsockname()[1]
      s.close()
      return port
  ```

### 1.4 ファイルI/O安全規約の遵守
- **PowerShellのエンコード汚染防止**:
  PowerShellでの `Add-Content` / `Set-Content` はUTF-8ファイルをCP932で破損させるため、ファイル追記はすべてPythonスクリプト（`open(path, "a", encoding="utf-8")`）を経由して実行する。

## 第2章: デュアルモデル協調型 24時間自律改善サイクル

高効率な自律実行を実現するため、安価で高速な **Flash層** と、高知能で俯瞰的な **Opus層** を明確に役割分担し、イベント・周期トリガーで動的に切り替える。

```
┌────────────────────────────────────────────────────────┐
│                        Opus層                          │
│     (全体最適設計、アーキテクチャ監査、ボトルネック分析)    │
└───────────┬────────────────────────────────┬───────────┘
            │ (バッチ設計・指示)              ▲ (監査報告・エスカレーション)
            ▼                                │
┌────────────────────────────────────────────┴───────────┐
│                        Flash層                         │
│     (30並列実行：バグ修正、テスト追加、静的解析、TDR登録)    │
└────────────────────────────────────────────────────────┘
```

### 2.1 役割分担マトリクス

| 評価軸 | Flash層 (Gemini 3.5 Flash) | Opus層 (Claude 4.6 Opus) |
|:---|:---|:---|
| **主な用途** | 実装、テストコード生成、TDR登録、静的解析修正 | 設計、マイルストーン再配置、技術負債監査、E2E分析 |
| **並列性** | 最大30並列（スケールアウト） | 単一スレッド（オーケストレータ） |
| **コスト** | 極めて低コスト（24時間連続稼働の主軸） | コスト高（週5時間/20回の上限枠で運用） |
| **監視対象** | `phase_state.json` の各タスクの成否 | 全体カバレッジ、品質ラチェット、憲法適合性 |

### 2.2 切り替えトリガー仕様
1. **定期トリガー (Opus起動)**:
   - 8時間周期（またはマイルストーン完了時）にOpusが自動で起動し、Flash層が積み上げたコードベースを監査する。
   - カバレッジの質的評価（カバレッジ改善規約におけるA/B/C分類の整合性）および技術負債台帳（TDR）の推移をレビューする。
2. **イベントトリガー (Opusへの緊急エスカレーション)**:
   - Flash層で **3回連続テストFAIL** が発生した場合。
   - カバレッジが **0.5%以上低下** し、減速モードでも回復しなかった場合。
   - 未分類の `Exception` がRouter層でキャッチされ、自動修復不能と判定された場合。

### 2.3 止まらない自走ポリシー（Gemini 3.5 Flashの最大限活用）
- **原則**: 何よりも「24時間自律実行プロセスを止めないこと」を最優先目標とする。
- **動的代替実行**: 
  - Opusの週次APIバジェット枠（週20回/5時間）の上限接近時や、夜間帯・大規模テスト稼働時においては、混同や手戻りのない範囲で、本来Opus層が担当する分析・レビュータスクを **Gemini 3.5 Flashへ一時的にフォールバック（代替）して自律実行** させる。
  - 実装側の設定モデルそのものは変更せず、実行スケジューラ内で一時的な代替指定を行い、APIレート制限によるフリーズや停止を完全に回避する。
- **タスクスケジューリングの動的調整**:
  - API負荷が高い時間帯や深夜は、並列数を30並列から10並列に落としつつも、Flashによる安全なテストカバレッジの向上（L1/L2タスク）を「止めずに」定常実行し続ける。

## 第3章: 4レベル自律判断基準と自動ブレーキ

完全な自律稼働において、安全弁（ブレーキ）と Git ロールバック機構による復旧を厳密に定義し、コード破壊のリスクをゼロにする。

### 3.1 4段階の意思決定レベル

- **Level 1 (完全自律 / Flash実行)**:
  - 対象: テストコードの追加、既存テストのパラメータ調整、ドキュメントの誤字修正。
  - 条件: プロダクションコード（`src/` や `backend/` のコアロジック）に一切の変更を加えないこと。
- **Level 2 (条件付き自律 / Flash実行)**:
  - 対象: 3ファイル以内の軽微なバグ修正、リファクタリング。
  - 条件: 修正後に `pytest` および `test_fitness_functions.py` が全PASSし、カバレッジが非退行であること。
- **Level 3 (要監査 / Opus承認)**:
  - 対象: 4ファイル以上の同時変更、DBスキーマのマイグレーション、共有基盤（Coordinator, model_governance 等）の変更。
  - 条件: Opusによる設計妥当性レビューを通過し、`sprint_design.md` が作成・合意されていること。
- **Level 4 (要決裁 / 人間承認)**:
  - 対象: 憲法（PROJECT_CONSTITUTION.md）の変更、Verified Factsの手動改訂、またはマイルストーンの削除・大幅なスキップ。
  - 条件: ユーザーのチャットによる明示的な承認（または `/goal` の明示的オーバーライド）が必須。

### 3.2 自動ブレーキと緊急停止 (Emergency Stop) と「自動回避」
- **テストFAIL監視と自動回避**:
  - サブエージェントが実行した pytest が3回連続で失敗した場合、即座にプロセスを止めるのではなく、まず失敗コミットを自動でロールバックし、エラー原因モジュールを次回バッチ対象から除外（ブラックリスト化）して他のモジュールのタスクで自走を継続する。
  - 自動回避不能なコアモジュールの破損である場合のみ、状態ファイル `phase_state.json` の `emergency_stop` を `true` に設定してサスペンドする。
- **カバレッジラチェット**:
  - カバレッジが前回のスナップショットから **2.0%以上低下** した場合、そのバッチの変更を自動でロールバックする。**0.5%低下** の場合は、並列数を30から10に縮小（スロットリング）しつつ、Gemini 3.5 Flashによる代替実行で様子を見ながら自律稼働を維持する。
- **ハング防止 (subprocess.Popenモック安全規約)**:
  モック化された `subprocess.Popen` が `poll()` や `readline()` のループで永久にハングするのを防ぐため、すべての外部プロセス実行テストには `pytest.ini` に `timeout = 60` を設定し、自動タイムアウトさせる。

### 3.3 自動ロールバック手順
自動ブレーキがトリガーされた場合、以下の手順でワーキングディレクトリを正常な状態に復元する。
1. 対象エージェントの作業用ブランチで `git stash` または `git reset --hard HEAD` を実行し、問題のコミットを破棄する。
2. 失敗したタスクIDとエラーログを `phase_state.json` の `history` に記録する。
3. ロールバックされたモジュールを「要Opusレビュー」としてマークし、次回バッチの対象から除外する。

## 第4章: 実装ロードマップと監視ダッシュボード仕様

24時間自律稼働の状態を可視化し、進捗状況を容易に把握するための管理仕様を定める。

### 4.1 進捗・品質監視ダッシュボードAPI
管理画面（Frontend）および管理コマンドから、以下のエンドポイントを介して自律稼働状況を監視する。

- **GET `/api/admin/autonomous/status`**:
  `phase_state.json` の中身を返し、現在のフェーズ、Milestone、並列エージェントの稼働状況を表示する。
- **GET `/api/admin/autonomous/metrics`**:
  テストPASS数、カバレッジ、技術負債（TDR）の推移を時系列で取得。
- **POST `/api/admin/autonomous/brake`**:
  手動で `emergency_stop` を発火させ、実行中のすべての並列エージェントを安全に停止・ロールバックする。

### 4.2 24時間自律実行の実装タイムライン
- **フェーズ5（卓越）**:
  並列分離テスト基盤の完全実装と、カバレッジ95%への引き上げ。
- **フェーズ6（本番検証）**:
  本番用1.05GB動画の編集イテレーションを24時間自律で回し、UI/UXストーリーのE2Eテスト合格率を95%以上に維持する。
- **フェーズ7以降**:
  Chaosエンジニアリング、負荷テスト、セキュリティ監査の自動実行への拡張。
