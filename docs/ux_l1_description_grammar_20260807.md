# description の述語と claim の対応 — 判定基準の決定記録

**2026-08-07 / P3 C-3。判断はユーザー、記録は Claude Code。**

`docs/ux_l1_claim_semantics_20260806.md`（`route_exists` の読み方）の続き。
あちらが「`claim` が何を確かめるか」を決めたのに対し、こちらは
**「その `claim` を貼ってよいかを誰が決めるか」**を決めた。

## 1. なぜ要ったか

`claim` は人が貼るラベルで、**description との対応を誰も検証していなかった。**
弱いラベルを選べば、主張の一部を捨てたまま PASS にできた。

```
description: "success=true"
claim:       response_field   ← CLAIM_SEMANTICS が「その値が何であるかは
                                 確かめない」と自ら明記しているラベル
→ PASS（success というフィールドが在るので）
```

`gate-verifier` 5回目の指摘。実在した3件:

| 項目 | description | 捨てられていた主張 |
|---|---|---|
| O11-L1-09 | `success=true` | **`=true`**（値） |
| O1-L1-04 | 動画リストに対応拡張子**のみ**含まれる | **「のみ」**（排他性） |
| O5-L1-05 | 固定解除APIが正常応答し locked_segments が**更新される** | **「更新される」**（状態遷移） |

## 2. 決めたこと

### 2.1 守り方 —— 機械と明記の両方

description の述語を**閉じた語彙**で書かせ、述語ごとに要求される `claim` を
機械で導く。語彙に無い書き方は `unparsed` として CI で落とす。

**マーカー検出（「強い述語だけ探す」）は採らなかった。** 辞書に無い語で強い主張を
書くと素通りするため。実際、この作業の下調べで作った最初のパターン表は
「4カテゴリ」を拾えなかった。**同じ型のポケットが5回連続で出ていたので、
検出ではなく閉包にした。**

語彙は `claim_audit.DESCRIPTION_GRAMMAR`。並び順が意味を持つ
（「〜のみ含まれる」は「〜含まれる」にも当たるので、強い述語を先に置く）。

### 2.2 語彙に無い述語が出たとき —— FAIL

CI が落ちる。**辞書に足して判定手段を決める**か、**登録済みの語で書き直す**かを
迫られる。免除は設けない。「判定していないものを PASS にしない」を機械にも
適用した形。

### 2.3 「そもそも測れない」はどの述語にも貼れる

`spec_incomplete` / `state_transition` / `idempotency` / `element_count` /
`parameter_coverage` は、述語が何であっても貼ってよい。

- **必ず FAIL に落ちるので偽の緑は作れない**
- 付け替えはラチェットの `substituted` が捕まえ、`--redeclare` の理由が残る
- PASS だった項目を落とすには `--tighten` も要る

述語の種類（何を主張しているか）と、測れるかどうか（照合先が特定できるか）は
**別の軸**。O9-L1-12「エクスポートAPIが正常応答」は述語としては経路の主張だが、
どの API を指しているかが仕様に書かれていない。この2つを1つの軸に押し込めると、
後者を表現できなくなる。

### 2.4 複合述語 —— すべての述語を覆う

「正常応答し、かつ locked_segments が更新される」のように述語が複数あるときは、
**1つでも測っていない述語があれば対応が取れていない**扱い。

## 3. 実在の4件をどう読んだか

| 項目 | 読み方 | 判定手段 | 結果 |
|---|---|---|---|
| **O11-L1-09** `success=true` | 値まで測る | 新 `response_value` | PASS `value_matched` |
| **O1-L1-04**「のみ」 | 集合一致を測る | 新 `value_exclusive` | PASS `value_set_matched` |
| **O5-L1-05**「更新される」 | 測れない | 新 `state_transition`（手段なし） | **FAIL** `unjudgeable` |
| **O6-L1-05**「4カテゴリ(a/b/c/d)が存在する」 | 列挙が在ればよい | 現状維持 `value_constraint` | PASS |

### 判定手段の意味（何を確かめ、何を確かめないか）

**`response_value`** — 宣言した値**以外のリテラルを返す経路がハンドラの
ソースに無い**ことを確かめる。「実行時に必ずその値になる」ではない。
動的に組み立てた値（`{"success": flag}`）は `<dynamic>` として拾い、
**そこで諦めずに FAIL にする。** 追えていないものを PASS に逃がすのが、
このフェーズで潰した型そのものだから。

実測: `POST /api/youtube/pre-plan` の `"success":` は1箇所で値は `True`。
`except` は2つあるが `success=False` を返す経路は無い。

**仕様としての帰結**: この API はエラーを `success=false` ではなく例外で返す。
後から `success=False` の経路を足すと CI が落ちる。

**`value_exclusive`** — 宣言した集合と**完全に一致する**リスト・リテラルが
実装にあることを確かめる。要素が現れるだけでは「のみ」を確かめたことにならない。
`*.mp4` と `.mp4` は同じものとして扱う（glob と拡張子の書き方の違いで
「集合が違う」と言うのは、測っている対象の取り違え）。

実測: `GET /api/pipeline/videos` が使うのは `["*.mp4","*.mov","*.mkv","*.avi"]` と
いう閉じたリテラル。

**仕様としての帰結**: 対応拡張子を増やすときは、検証項目の宣言も同じ PR で
直すことが強制される（`--redeclare` で理由が残る）。

**`state_transition`** — 判定手段なし。1回の静的走査では「返る」としか言えず、
「更新される」と区別が付かない。兄弟項目 O5-L1-04 は「locked_segments が**返る**」で
存在の主張なので、**2件の書き分けが仕様として保たれる。**
