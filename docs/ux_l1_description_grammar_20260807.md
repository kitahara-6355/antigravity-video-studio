# description の述語と claim の対応 — 判定基準の決定記録

**2026-08-07 / P3 C-3。判断はユーザー、記録は Claude Code。**

`docs/ux_l1_claim_semantics_20260806.md`（`route_exists` の読み方）の続き。
あちらが「`claim` が何を確かめるか」を決めたのに対し、こちらは
**「その `claim` を貼ってよいかを誰が決めるか」**を決めた。

## 1. なぜ要ったか

`claim` は人が貼るラベルで、**description との対応を誰も検証していなかった。**
弱いラベルを選べば、主張の一部を捨てたまま PASS にできた。

```
description: "success=true"
claim:       response_field   ← CLAIM_SEMANTICS が「その値が何であるかは
                                 確かめない」と自ら明記しているラベル
→ PASS（success というフィールドが在るので）
```

`gate-verifier` 5回目の指摘。実在した3件:

| 項目 | description | 捨てられていた主張 |
|---|---|---|
| O11-L1-09 | `success=true` | **`=true`**（値） |
| O1-L1-04 | 動画リストに対応拡張子**のみ**含まれる | **「のみ」**（排他性） |
| O5-L1-05 | 固定解除APIが正常応答し locked_segments が**更新される** | **「更新される」**（状態遷移） |

## 2. 決めたこと

### 2.1 守り方 —— 機械と明記の両方

description の述語を**閉じた語彙**で書かせ、述語ごとに要求される `claim` を
機械で導く。語彙に無い書き方は `unparsed` として CI で落とす。

**マーカー検出（「強い述語だけ探す」）は採らなかった。** 辞書に無い語で強い主張を
書くと素通りするため。実際、この作業の下調べで作った最初のパターン表は
「4カテゴリ」を拾えなかった。**同じ型のポケットが5回連続で出ていたので、
検出ではなく閉包にした。**

語彙は `claim_audit.DESCRIPTION_TEMPLATES`。**文全体**に一致する正規表現で、
部分一致は認めない。

**この層は3回作り直した。2回とも「同じ主張が書き方の違いで強弱に振れる」で
破られている。**

| 回 | 破られ方 |
|---|---|
| 10 | 文末の動詞しか見ていなかった。`…正常応答し success=true が返る` で値の主張が消えた（空白の有無で振れる） |
| 11 | スロット検査が文末アンカーで、句点を1文字足すと素通りした（末尾表現で振れる） |
| 12 | マーカーに**当たらなかった部分が黙って捨てられた**。読点で強い主張を節の外へ押し出せた |

| 13 | マッチは文全体になったが、**検査は名前付きスロットだけ**だった（無名部分・括弧の中へ逃がせる） |
| 14 | 強い述語の検査が**6本の語彙**に依存。語彙外（`以外` `一致する` `巻き戻して` `5個まで`）は名詞句に吸収される |

文全体を見るようにした。テンプレートは節の区切り（読点・句点）を許さないので、
**一文一主張**になり「強い主張を別の節へ逃がす」経路が構造的に消える。
さらに、強い述語（`更新` `以内` `限ら` `のみ` `=` `件` `可能`）を**文全体**に走査し、
テンプレートが引き受けていない述語が残っていたら一致させない。

### 語彙では閉じきらない——だから description をラチェットで固定する

14回目の指摘: この検査は**語彙**（6本の正規表現）に依存していて、語彙外の述語
（`以外` `一致する` `巻き戻して` `5個まで`）は名詞句に吸収される。**語彙を足しても、
次の語彙外の述語で同じことが起きる。4回続けてそうだった。**

テンプレート検査が保証できるのは「**新しい**項目が最低限の形をしていること」まで。
**既存の項目の主張が黙って変わらないこと**は、ラチェットの仕事にした。
`description` を `DECLARATION_KEYS` に入れたので、書き換えは `substituted` として
検出され、`--redeclare` の理由と before/after が永久に残る。

    [宣言の差し替え] O1-L1-01: description=動画一覧APIが正常応答を返す
      → description=mp4以外は拒否され5個までに制限される動画一覧APIが正常応答を返す

### 名詞句も辞書で閉じる

15回目の指摘: ラチェットは**既存項目**しか守らない。**新規項目**は語彙外の述語で
強い主張を書いても audit が「対応が取れている」と言い、`--update-baseline` 一発で
恒久に緑にできた。

**ユーザー判断（2026-08-07）: 名詞句も辞書で閉じる。** `NOUN_PHRASES` に登録された
名詞句（93種）以外は `unparsed`。**辞書は「名詞句 → 使ってよいテンプレート」まで
持つ**——グローバルな集合にしていた頃は、判定不能の項目のために登録した名詞句を
PASS できる弱いテンプレートへ移せた（16回目）。テンプレートの**無名の前置**にも
同じ検査が掛かる（`{_NP}正常応答し…` の前半が無検査だった）。新しい項目を足すときは名詞句を登録する——
**その登録が、人が主張を読む機会**になる。

### 宣言との突き合わせ（`slot_not_declared`）

description が書いている名前は、項目が宣言しているものと一致していなければならない。

- **スロットが ASCII 識別子** → `response_field` に含まれること
- **名詞句に埋め込まれた小文字スネークの語** → 同じく `response_field` に
  含まれること。スロット全体が識別子のときしか見ていなかったので、
  `候補にtimestampフィールドが存在する` に `response_field: type` を宣言しても
  通った（18回目）。`候補に` を足すか足さないかで強弱が振れていた。
  `API` `BGM` `SEO` のような略称・製品名は名前の一部なので対象外——
  そちらは `value_note` が引き受ける
- **値の指定** → 書かれた値が `expected_value` と一致すること
- **列挙の実在** → 列挙が `value_literals` と集合一致すること
- **名詞句が指す経路** → `PHRASE_ENDPOINTS` に登録した endpoint と一致すること。
  `動画一覧APIが正常応答を返す` に `endpoint: /api/health` を宣言しても
  通っていた（18回目）。**未登録は「無検査」ではなく不合格**——`get()` が None の
  ときに素通りさせていたので、辞書に無い名詞句（`エクスポートAPI`）は endpoint を
  何と宣言しても通った（22回目）。**テンプレート単位で引く**——同じ `locked_segments` でも
  「経路＋フィールド」は lock、「経路＋状態遷移」は unlock を指す

**免除はスロットだけ。** `{prefix}正常応答し…` の前置はどこでも宣言と
突き合わされないので、識別子でも辞書登録を要求する（20回目）。
前置が指す経路も `PHRASE_ENDPOINTS` に登録・照合する。

**純粋な UI 名（`進捗バー` `CTR予測`）は DOM の主張に限る。** レスポンスの
フィールドを測る claim を貼れば、無関係な API の実在で緑にできた（20回目）。
判定は**小文字スネークの語の有無**で行う——ASCII トークンの有無にしていたので、
大文字の略称を含む名前（CTR / SEO / SRT / TXT / Whisper）だけ固定から
漏れていた（21回目）。

**小文字スネークの語を含む名詞句は、レスポンスの主張に固定する。**
`動画一覧にvideos配列が存在する` に `dom_exists` を貼れば testid 1本で緑になり、
埋め込みフィールド名も endpoint も照合されなかった（23回目）。接尾辞が
`配列` か `フィールド` かで強弱が振れていた。**例外は `DOM_PHRASES` に登録する**
——`diffコンテナ` の `diff` はフィールド名ではないが、機械には見分けられない。

**空スロットも通さない。** 辞書にも経路にも掛からないので、「未登録＝無検査」を
塞いだのと同じ場所に「空＝無検査」が残っていた（23回目）。

**列挙の件数も照合する。** `\d+カテゴリ(...)` の先頭の数値はどの層でも
見ていなかったので、実装が4種でも「99カテゴリ」と主張したまま緑にできた（21回目）。

**ASCII 識別子のスロットを辞書検査から免除してよいのは、その名前が実際に宣言と
突き合わされるテンプレートだけ。** 免除の根拠は「`slot_not_declared` が照合するから」
なので、照合が走らないテンプレート（経路のみ・リクエスト契約・保存キーの実在ほか）で
免除すると素通りになる。19回目に指摘された:
`analyze_scriptAPIが正常応答する` はハイフンをアンダースコアに替えるだけで
検査が消えていた。

**文末だけを見ない。** 最初の実装は「先に当たったパターンを採る」形にしていたが、
それは文末の動詞を閉じただけで主張の中身は閉じていなかった。`success=true` は
強い述語に当たるのに、`…正常応答し success=true が返る` と書くと
「経路＋フィールド」に落ちて値の主張が消えた（gate-verifier 10回目）。
**同じ主張が空白の有無で強弱に振れていた。** いまは文中の述語を**すべて**拾い、
その組み合わせに対して claim を要求する。組み合わせが未登録なら `unparsed`。

### 機械が型付けできないスロットは人に宣言させる

`hook_score を返す`（フィールドの実在）と `ステータスが completed を返す`
（値の主張）は、どちらも「〜を返す」で終わる。`completed` が値なのか
フィールド名なのかを機械は知らない。

**ユーザー判断（2026-08-07）: 判別できないものは明記させる。**
`value_note` に「この文が値の主張かどうか」を書く。**空欄は機械が許さない。**
要求する範囲は2つ。

- **「〜を返す／含まれる」の手前が ASCII 識別子でないもの**（10件）。
  検査は**文末に固定しない**——以前は文末アンカーで見ていたので、句点を1文字
  足すだけで「照合対象なし」に落ち、検査ごと素通りした（gate-verifier 11回目）
- **「〜が存在する」でスロットに ASCII トークンが混じるもの**（18件）。
  `ステータス表示が completed で存在する` ＋ `dom_exists` ＋ testid で、
  値の主張を要素の実在で緑にできるため。ユーザー判断で、純粋な UI 名
  （`進捗バーが存在する`）は対象外とした。**残る穴**: 値を日本語で書いた場合は
  すり抜ける

宣言は `DECLARATION_KEYS` に入れてラチェットが固定するので、消したり
書き換えたりすれば `substituted` が捕まえて `--redeclare` の理由が残る。

### 2.2 語彙に無い述語が出たとき —— FAIL

CI が落ちる。**辞書に足して判定手段を決める**か、**登録済みの語で書き直す**かを
迫られる。免除は設けない。「判定していないものを PASS にしない」を機械にも
適用した形。

### 2.3 「そもそも測れない」はどの述語にも貼れる

`spec_incomplete` / `state_transition` / `idempotency` / `element_count` /
`parameter_coverage` は、述語が何であっても貼ってよい。

- **必ず FAIL に落ちるので偽の緑は作れない**
- 付け替えはラチェットの `substituted` が捕まえ、`--redeclare` の理由が残る
- PASS だった項目を落とすには `--tighten` も要る

述語の種類（何を主張しているか）と、測れるかどうか（照合先が特定できるか）は
**別の軸**。O9-L1-12「エクスポートAPIが正常応答」は述語としては経路の主張だが、
どの API を指しているかが仕様に書かれていない。この2つを1つの軸に押し込めると、
後者を表現できなくなる。

### 2.4 複合述語 —— すべての述語を覆う

「正常応答し、かつ locked_segments が更新される」のように述語が複数あるときは、
**1つでも測っていない述語があれば対応が取れていない**扱い。

## 3. 実在の4件をどう読んだか

| 項目 | 読み方 | 判定手段 | 結果 |
|---|---|---|---|
| **O11-L1-09** `success=true` | 値まで測る | 新 `response_value` | PASS `value_matched` |
| **O1-L1-04**「のみ」 | 集合一致を測る | 新 `value_exclusive` | PASS `value_set_matched` |
| **O5-L1-05**「更新される」 | 測れない | 新 `state_transition`（手段なし） | **FAIL** `unjudgeable` |
| **O6-L1-05**「4カテゴリ(a/b/c/d)が存在する」 | 列挙が在ればよい | 現状維持 `value_constraint` | PASS |

### 判定手段の意味（何を確かめ、何を確かめないか）

**`response_value`** — 宣言した値**以外のリテラルを返す経路がハンドラの
ソースに無い**ことを確かめる。「実行時に必ずその値になる」ではない。
動的に組み立てた値（`{"success": flag}`）は `<dynamic>` として拾い、
**そこで諦めずに FAIL にする。** 追えていないものを PASS に逃がすのが、
このフェーズで潰した型そのものだから。

実測: `POST /api/youtube/pre-plan` の `"success":` は1箇所で値は `True`。
`except` は2つあるが `success=False` を返す経路は無い。

**仕様としての帰結**: この API はエラーを `success=false` ではなく例外で返す。
後から `success=False` の経路を足すと CI が落ちる。

**`value_exclusive`** — 宣言した集合と**完全に一致する**リスト・リテラルが
実装にあることを確かめる。要素が現れるだけでは「のみ」を確かめたことにならない。
`*.mp4` と `.mp4` は同じものとして扱う（glob と拡張子の書き方の違いで
「集合が違う」と言うのは、測っている対象の取り違え）。

実測: `GET /api/pipeline/videos` が使うのは `["*.mp4","*.mov","*.mkv","*.avi"]` と
いう閉じたリテラル。

**仕様としての帰結**: 対応拡張子を増やすときは、検証項目の宣言も同じ PR で
直すことが強制される（`--redeclare` で理由が残る）。

**`state_transition`** — 判定手段なし。1回の静的走査では「返る」としか言えず、
「更新される」と区別が付かない。兄弟項目 O5-L1-04 は「locked_segments が**返る**」で
存在の主張なので、**2件の書き分けが仕様として保たれる。**
