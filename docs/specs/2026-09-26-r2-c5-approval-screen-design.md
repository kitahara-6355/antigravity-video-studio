# R2-C5 設計案 — 承認画面でモデルを見せ、その場で昇格してやり直す（**提案・未承認**）

作成 2026-09-26（クラウドのセッション）。**中間ゲート（C1〜C3）の判断の後に着手する**（2026-09-19 のユーザー決定: 「C5 は中間ゲートの後」）。
実装はしていない。ここに書くのは、着手した日に迷わないための設計と PR の分け方。

## 条件（正典の原文）

> **承認画面から、その提案がどのモデルで出たかが見え、その場で昇格を指示できる。** 不満 → 昇格 → やり直しが1画面で完結する。
> あわせて**なぜそのモデルになったか**（段の宣言どおりか、降格ならその理由 — 503・429 など）が実行記録に残り、承認画面から見える（D-39）。

分解すると4つ:

| # | 要るもの | いまの状態 |
|---|---|---|
| a | 提案ごとに**工程別のモデル**が見える | 記録には既にある（`run.json` の `stages[].model / tier / models_observed / model_mismatch / model_unverified`）。**画面が無い** |
| b | **なぜそのモデルか**（宣言どおりか、降格ならその理由）が記録に残る | **残らない**（D-39）。降格は `model_governance._record_event` のメモリ上のイベント（200件で切り詰め）とコンソールにしか出ない |
| c | 画面から**昇格を指示**できる | CLI の `model_policy --up <工程> --reason` はある（履歴は `.claude/model_escalations.jsonl`）。**画面の口が無い** |
| d | **やり直し**まで同じ画面で完結する | 提案を作り直す口が無い。やり直すと提案の指紋が変わるので、**承認は自動で無効になる**（C1 の門がそのまま効く） |

## 設計

### b. 降格の理由を記録に残す（D-39・最初に作る）

- 課金の絞り口は `cost_guard` の台帳（`.claude/cost_ledger.jsonl`・1呼び出し1行）で、`RunRecorder._close_stage` が工程ごとに行を拾っている。
  **理由も同じ道に載せる**:
  - `GovernedModelsProxy` がフォールバックで成功したとき、その呼び出しの台帳行に `requested`（宣言したモデル）・`fallback_reason`（`503` / `429` / `404` / `quota_proactive`）・`attempts` を足す
  - `_close_stage` が工程の行から `fallbacks: [{from, to, reason, count}]` を作り、`model_reason` を `declared`（宣言どおり）/ `fallback`（降格）/ `observed`（宣言なし）にする
- **メモリ上のイベントには頼らない**（プロセスをまたがず、200件で切れる）。台帳は既に工程との対応が取れている

### a + c + d. 承認画面

- **置き場所: FastAPI が返す1枚の HTML ＋ JSON API**（`/api/r2/runs/{run_id}` 系）
  - 理由: `frontend/`（Vite/React）には **CI が無い**（gate-verifier の注意書き）。API を pytest で固め、画面は薄く保つ
  - 画面の検証は Playwright で行う（Chromium はクラウドにも入っている）。スクリーンショットを DoD の成果物にする
- 画面に出すもの（1本の提案につき）:
  - プレビュー（`<video>`）・品質点・書き出しのモード
  - 工程ごとの行: 工程名 / 段 / 宣言したモデル / 実際に動いたモデル / **理由**（宣言どおり・降格（503）・未検証）/ 原価
  - 承認フォーム（CLI の `--approve` と同じ門: `--by` 必須・開示の判断必須）
- 昇格とやり直し:
  - 行ごとに「この工程を1段上げてやり直す」→ 理由の入力が必須（`model_policy --up` と同じ規則。履歴も同じ jsonl）
  - **pro 段は課金。** 押す前に見積もり（`cost_guard` の単価表）と残予算を出す。予算が無ければ押せない（fail-closed）
  - やり直しは、その工程から先を再実行して**新しい提案**を作る。古い提案は `proposal_history/` に残し、`--trace` に出す（C2 の延長）
  - 既存の承認は指紋が変わるので自動で効かなくなる。**画面でも「承認し直しが要る」と出す**

### 守る範囲（C1 と同じ考え方で、先に書く）

- この画面は**本人がローカルで使う**もの。認証は付けない（`127.0.0.1` にだけ bind。外に出す場合は別フェーズ）
- 画面からの承認は CLI と**同じ関数**を呼ぶ（門を2つにしない）。limits #5「承認は CLI だけ」は C5 で外す

## PR の分け方（案）

1. **D-39**: 台帳行に降格の理由 → `run.json` に `fallbacks` / `model_reason`。`--trace` と `run_record --resume` にも出す（バックエンドだけ・クラウドで完結）
2. **読み取り API ＋ 画面（見るだけ）**: 提案・工程別モデル・理由・プレビュー。Playwright のスクショ
3. **画面から承認**: CLI と同じ門。409/400 の文言を CLI と揃える
4. **昇格してやり直す**: 工程から先の再実行・提案の履歴・見積もりと予算の確認
5. gate-verifier → ゲート報告（R2 の終了）

## 課金（計画段階で出す — 憲法第3条）

- 1〜3 は**課金なし**（ダミーキーで検証できる）
- 4 の検証には**実キーの実走が要る**: 昇格 → やり直しを1回（standard → premium は無料枠、premium → pro は課金）。
  見積もりは1回あたり数円〜数十円。**R2 の予算 `R2-approval`（¥1,000 のうち使用 ¥4.71）の範囲内**に収まる見込み
- 実キーはクラウドに無いので、**4 の実走の検証はローカル**で行う

## 追記（2026-09-26・検証4周の後・ユーザー決定）

gate-verifier の2〜4周目はすべて同じ類（AI の出力が提案に届いていないのに「宣言どおり」）だった。経路を列挙して塞ぐ限り次の経路が出るので、**作りを変えた**:

- **「宣言どおり」は断定ではなく証拠で決める。** 工程は「採用した AI の出力の件数」（`ai_accepted`）を `ctx.ai_accepted[印]` で報告し、coordinator が記録の工程に写す
  - 校閲: `ai_proofreader` の `accepted_items`（採用した項目の数）。全バッチ失敗・空リスト・鍵違い・範囲外は 0
  - YouTube 最適化: 応答の dict に中身のある鍵（titles / tags / description / chapters）の数。0 なら形だけなのでスタブに落とす
- `model_reason` の順: **stub（`ai_skipped` か `ai_accepted == 0`）** → partial → fallback → mismatch → unverified → declared → observed
- 画面と `--trace` は「宣言どおり（採用 N 件）」／「宣言どおり（採用の証拠なし — 件数を報告しない工程）」と出す
