# ブリーフィングプロトコル — タスクチャット開始時の情報表示

> **バージョン**: 1.3.0
> **最終更新**: 2026-05-05
> **参照元**: GEMINI.md「チャット開始時プロトコル」

---

## モード判定ロジック

1. VerifiedFacts (category=progress) から完了済みタスクを取得
2. MASTER v3.6 と突合し、未完了の次タスクを特定
3. 次タスクの MASTER 記載を確認:
   - テスト名 + 検証基準が**1行ずつ定義**されている → 🟢 実装 (Sonnet)
   - タスク名 + ゴールのみ。具体的手順がない → 🔴 設計 (Opus)
   - VerifiedFacts に当該タスクのブロッカーがある → 🔴 設計 (Opus)

※【重要】🔴設計モードの場合、GEMINI.md の IDR 3ステップ防衛に従い、既存の合意済み設計書を必ず検索すること。

ユーザーが設計判断を行うために必要な全情報を表示する。

```markdown

UXストーリー O-X: 「[UXストーリーの1文要約]」
憲法 §X.X: [該当条項名]

### 前回のセッション
[VF category=progress の最新エントリから要約]

### 現在地
Phase X > MX.X > Sprint X.X.X > **[Worker名 カテゴリ]**
全体: XX/1,257 (X.X%) | pytest-cov: XX% | ビジョン: XX%

### 🏷️ タスクモード: 🔴 設計 (Opus推奨)
理由: [なぜ設計が必要か]

### 本チャットの目標
[このチャットで達成すべきこと]

### 📊 FV品質基準 (対象)
- FV-XX [項目名] ([合格基準]) — 未検証/PASS/FAIL

### 👁️ ユーザー判断を求める場面
- [設計A vs 設計Bの選択]
- [パラメータの妥当性判断]

### 💡 関連VerifiedFacts
- VF: [関連する確定事実] (該当がある場合のみ)

### ⚠️ 注意点
- [ファイル共有や依存関係の警告] (該当がある場合のみ)
```

## 🟢 実装モード (Sonnet) — 最小指示 + 充実レポート

### 開始時: 最小指示のみ

ブリーフィングは不要。以下の情報だけでサイレント実行を開始する:

```
対象: MASTER v3.6 Sprint X.X.X [Worker] [カテゴリ] (LXXX-LXXX)
テストファイル: tests/test_workers/test_xxx/test_cX_xxx.py
参照実装: backend/xxx.py
EP条件: GEMINI.md §EP参照
```

### 完了時: ✅ 完了レポート

```markdown
## ✅ 完了レポート

### 結果サマリー
[Worker名] [カテゴリ]: **X/X PASS**

### テスト結果
tests/test_xxx.py
  ✅ test_xxx_xxx
  ✅ test_xxx_xxx
  ...

### カバレッジ変動
[対象ファイル]: XX% → XX% (+XX%)

### VerifiedFacts記録
progress: "[Worker] [カテゴリ]: X/X PASS, branch cov XX%" (証拠: pytest出力)

### 次タスクへの申し送り
- [発見した問題や推奨事項]
- [次カテゴリへの依存情報]
```

### 異常時: 🆘 ヘルプレポート

EP条件に該当した場合、または自力解決できない問題が発生した場合:

```markdown
## 🆘 ヘルプレポート

### 状況
[Worker名] [カテゴリ]: **X/X PASS, X FAIL**

### 自力解決できない問題
[テストID]: [問題の具体的な説明]
修正方針が複数あり、設計判断が必要:
  A) [方針A]
  B) [方針B]

### 試したこと
- [A案の結果]
- [B案の結果]

### 必要な判断
[ユーザーに求める具体的な判断内容]
[FV項目やUXストーリーへの影響があれば記載]

### 現時点のVF記録
progress: "[Worker] [カテゴリ]: X/X PASS (XXX未完)" (証拠: pytest出力)
```

## 実状確認 (両モード共通)

チャット開始時に以下を**必ず**実行し、VF記載と現実の突合を行う:

```powershell
# 必須: 前回の完了テストが今も通るか確認（軽量版: カバレッジなし）
// turbo
cd backend; python -m pytest tests/test_workers/ -q --tb=line
```

カバレッジ計測(`--cov-branch`)はMilestone完了ゲート時のみ実行する。

不一致があれば、VFの記載をpytest結果で上書きしてからブリーフィング/実行を開始する。

## VerifiedFacts 記録ルール

> [!CAUTION]
> **VERIFIED_FACTS.md を直接テキスト編集してはいけない。**
> 必ず以下のPythonコードまたは同等のAPI経由で記録すること。
> 手動編集するとJSON Indexとの乖離が発生し、DreamEngineが破損する。

### 完了記録 (category=progress)

```python
verified_facts_store.add_fact(
    category="progress",
    content="SmartCutWorker C2コアロジック: 8/8 PASS, branch cov 62%",
    evidence="pytest tests/test_smartcut/test_c2_core_logic.py → 8 passed, 0 failed",
    source="development_session",
    confidence=1.0,  # pytest結果は確定事実
)
```

### ブロッカー記録 (category=progress)

```python
verified_facts_store.add_fact(
    category="progress",
    content="SmartCutWorker C2-06: BLOCKED — _calc_density() ZeroDivisionError, 設計判断待ち",
    evidence="pytest test_c2::test_text_density_score → ZeroDivisionError at L142",
    source="development_session",
    confidence=1.0,
)
```

### 学習記録 (category=lesson)

```python
verified_facts_store.add_fact(
    category="lesson",
    content="MIN_SEGMENT_DURATION=1.0のハードコードは設定化すべき",
    evidence="SmartCutWorker C2-05テスト中にconftest依存を確認",
    source="development_session",
    confidence=0.8,
)
```

## チャット完了時ハンドオフプロトコル（v1.1新設）

### 発動条件

以下のいずれかを満たしたとき、本チャットの役割は終了と判定する:

1. ブリーフィングで宣言した「本チャットの目標」を達成した
2. VerifiedFactsにprogress事実を記録した
3. 次のタスクが**異なるモード**（設計↔実装）または**異なるMilestone**に属する

### 実行手順

完了レポートの末尾に以下を追加する:

#### Step 1: チャット移行提案

```markdown
### 📤 チャット移行提案

本チャットの目標は達成されました。次タスクは性質が異なるため、新規チャットへの移行を推奨します。

| 項目 | 本チャット | 次チャット |
|:---|:---|:---|
| タスク | [完了したタスク] | [次のタスク] |
| モード | 🟢/🔴 | 🟢/🔴 |
| 推奨LLM | Sonnet/Opus | Sonnet/Opus |
| 理由 | — | [なぜ新規チャットが必要か] |
```

#### Step 2: 次チャットの初回プロンプト生成

以下のテンプレートに従い、**コピー可能な初回プロンプト**をチャットメッセージ内にコードブロックで直接表示する:
（アーティファクトは不要。コピーの手間を最小化する）

```markdown
Antigravity Video Automation Pipelineの改善タスクを継続します。
GEMINI.mdの「チャット開始時プロトコル」に従ってブリーフィングを実行してください。

## 参照ファイル
- GEMINI.md
- backend/agents/memory/VERIFIED_FACTS.md
- Human01_Official Artifact/最新の開発推移表 (※ファイル名は `開発推移表_*.md` で検索)
- MASTER が配置されているフォルダ (※推移表からファイル名を特定)
- .agent/workflows/briefing-protocol.md

## 手順
1. VerifiedFacts の category=progress を確認し、完了済みタスクを把握
2. MASTER v3.6の[次タスク該当セクション]を参照し、次の未完了タスクを特定
3. モード判定（設計/実装）を行い、ブリーフィングを表示
4. ブリーフィング表示後、ユーザーの指示を待つ

## コンテキスト（前チャットからの申し送り）

### 前チャットの変更ファイル
[変更したファイルパスを列挙（次チャットが参照すべきファイルを明示）]

### 完了済み
[VFのprogress事実を要約]

### カバレッジ
[最新のpytest/branch cov数値]

### 本チャットの目標
[MASTERから導出した次タスクの目標]

### テストファイル配置
[関連テストファイルのパス]

### 注意事項
[ブロッカー、依存関係、特記事項]
```

#### Step 3: ユーザー確認

プロンプト生成後、ユーザーに「新規チャットに貼り付けて開始してください」と案内する。

### 補足ルール

- ハンドオフプロンプトには**VFに記録済みの事実のみ**を含める（未検証の推測は含めない）
- MASTER行番号を具体的に指定し、次チャットが正確なセクションを参照できるようにする
- 推奨LLMモデルは、ブリーフィングプロトコルのモード判定ロジックに従う
- **3点連動義務**: 設計チャット完了時は以下のチェックリストを完了すること:
  - ☐ MASTER該当Milestoneにテスト名+検証基準+設計書ファイル名を追記
  - ☐ 開発推移表に `[M番号]` タグ付きエントリを追加
  - ☐ ハンドオフプロンプトに設計書パスを明記
  - 3点揃わなければチャット完了とみなさない (GEMINI.md §チャット開始時プロトコル Step 5)

### レポート作成の半自動提案 (v1.3新設)

以下のいずれかに該当する場合、チャット完了時に
「報告レポートの作成を推奨します」とユーザーに提案すること:

1. ユーザーから設計方針の指摘・修正があった場合
2. エスカレーション条件(EP)に該当した場合
3. 3回以上のテストFAIL→修正サイクルが発生した場合
4. 新しいルール・規約・ベストプラクティスが確立された場合
5. 障害(CP932汚染、サーバー停止等)が発生し復旧した場合

> **注**: レポート作成は提案のみ。最終判断はユーザーが行う。
> レポート作成指示があった場合は、GEMINI.md §チャット開始時プロトコル Step 5 の
> 「報告レポートの原文記録」ルールに従い、重要な発言原文を引用して記録すること。

## ブリーフィング様式遵守ルール (v1.3新設)

- 🔴設計モード/🟢実装モードの出力テンプレートは本プロトコル§のコードブロック内の形式を**厳密に**遵守すること
- 独自形式でのブリーフィング出力は禁止
- タスクモード(🔴/🟢)は必ず表示すること
- VF照合結果は必ず記載すること
