# フェーズ完了プロトコル

## 概要
フェーズに分けた段階的実装において、各フェーズの品質を担保し、安定稼働を確認してから次のフェーズに進むためのプロトコル。

## フェーズ移行の3ステップ

### Step 1: 実装完了確認
- [ ] 当該フェーズの全タスクが完了
- [ ] コードにエラーがないこと（import、構文）
- [ ] 既存機能が壊れていないこと

### Step 2: 品質チェック実行
```powershell
# バックエンドテスト
cd backend
python -m pytest tests/ -v

# 品質監査スクリプト
python quality_audit.py
```

**品質基準**:
- 全テストがパス
- 品質スコア 9.0/10.0 以上
- 陳腐化警告がないこと
- **FV(機能実効性検証)**: 当該Phaseで完了したWorkerの全FV項目がPASS
- **UXストーリー充足**: 当該Phaseで完了した機能の関連UXストーリー(O-1〜O-12, A-1〜A-7)が全PASS

### Step 3: 安定稼働確認
```powershell
# サーバー再起動
# turbo
cd backend; python -m uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

**確認項目**:
- サーバーが正常起動すること
- 主要APIエンドポイントが応答すること
- ブラウザUIが正常表示されること

### Step 3.5: 設計妥当性レビュー（v2.0新設）

実装結果と監査結果に基づき、初期設計の妥当性をレビューする。

#### 3.5.1 レビュー対象

| 観点 | 質問 | 判定基準 |
|:---|:---|:---|
| FV合格率 | FV検証で初回合格率は70%以上か？ | <70% → テスト設計見直し |
| UXストーリー充足 | E2E初回実行で全UXストーリーPASSか？ | FAIL項目あり → UI/ワーカー設計見直し |
| 修正イテレーション回数 | FV/E2E合格までの修正回数は3回以内か？ | >3回 → 当該Worker設計見直し |
| 分岐カバレッジ乖離 | 実カバレッジとAST実測の差は10%以内か？ | >10% → 分岐計測再実行 |
| 時間予算遵守 | Worker実行時間が予算内か？ | 超過 → 性能設計見直し |

#### 3.5.2 設計見直し判定

```
設計妥当性レビュー結果:
├── 全問題なし → 次Phase移行
├── 軽微（1-2項目のみ） → 改善バックログ追加 → 次Phase移行
└── 重大（3項目以上 or FV合格率<50%）
    → 設計見直し必要 → 改訂計画作成 → ユーザー承認 → 修正実行 → 再レビュー
```

#### 3.5.3 レビュー結果テンプレート

```markdown
## Phase X 設計妥当性レビュー

### 初期設計 vs 実装結果
| 観点 | 初期設計の想定 | 実装結果 | 判定 |
|:---|:---|:---|:---:|

### 設計見直し必要性
- [ ] 見直し不要 → 次Phase移行
- [ ] 軽微修正 → バックログ追加
- [ ] 設計見直し必要 → 改訂計画作成

### 次Phaseへの教訓
- ...
```

## 改善タスクの積み上げと総合評価

### 各フェーズでの積み上げ

各フェーズで発見された改善点は **improvement_backlog.md** に記録する。

```markdown
| ID | フェーズ | 改善内容 | 優先度 | 影響範囲 |
|:---|:---|:---|:---|:---|
| IMP-001 | Phase 1 | ロギング強化 | 中 | 局所 |
| IMP-002 | Phase 3 | プラグイン並列化 | 低 | 全体 |
```

### 最終Phase完了後: 総合評価

全フェーズ完了後、以下の手順で積み上げ改善タスクを評価する:

#### Step A: 影響範囲分析

| 影響範囲 | 説明 | 判定 |
|:---|:---|:---|
| **局所** | 単一ファイル/モジュール内 | 一気通貫実装OK |
| **コンポーネント** | 複数ファイルにまたがるが1機能内 | 一気通貫実装OK |
| **全体** | アーキテクチャ設計に影響 | **設計見直し検討** |

#### Step B: アーキテクチャ影響判定

```
「全体」影響の改善タスクが存在する?
    ├── Yes → Step C: 設計見直し検討
    │              ↓
    │          見直しが必要?
    │              ├── Yes → アーキテクチャ再設計 → 追加実装
    │              └── No → Step D: 一気通貫実装
    │
    └── No → Step D: 一気通貫実装
```

#### Step C: 設計見直し検討

「全体」影響の改善タスクについて、以下を評価:

| 評価項目 | 質問 |
|:---|:---|
| 必要性 | この改善をしないと品質基準を満たせないか？ |
| 影響 | 既存実装のどれだけを変更する必要があるか？ |
| コスト | 追加の実装時間はどれくらいか？ |
| リスク | 変更によるデグレードリスクは？ |

**判定基準**:
- 影響が実装済みコードの30%以上 → 設計見直し推奨
- 影響が30%未満 → 一気通貫実装で対応可能

#### Step D: 一気通貫実装

```powershell
# 改善タスクを優先度順に実装
# 高 → 中 → 低 の順

# 各改善後にテスト実行
python -m pytest tests/ -v
```

#### Step E: 最終品質チェック

全改善タスク完了後、アーキテクチャ全体の品質チェックを実行:

```powershell
# 全体品質監査
python quality_audit.py --full

# 統合テスト
python -m pytest tests/integration/ -v

# エンドポイント疎通確認
python test_all_endpoints.py
```

**最終品質基準**:
- 品質スコア **9.5/10.0** 以上
- 全テストパス
- 陳腐化警告ゼロ
- サーバー安定稼働
- **FV全項目PASS** (FV-01〜FV-20)
- **UXストーリー全充足** (O-1〜O-12, A-1〜A-7)
- **設計妥当性レビュー** 全Phase完了

```
    ↓

    ├── Yes → Step C: 設計見直し検討
    └── No → Step D: 一気通貫実装
    ↓
Step E: 最終品質チェック
    ↓

```

### Step 3.6: DreamEngine強制実行 — v2.1新設

Phase完了の節目で、そのPhaseで得られた知見をDreamEngineで整理・永続化する。

```python
# Phase完了時にDreamサイクルを強制実行
from agents.dream_engine import dream_engine
result = await dream_engine.run_dream_cycle(force=True)
print(f"Dream完了: {result.gather_count}件のシグナル処理, "
      f"新規ファクト: {result.consolidation.new_facts}件")
```

**目的**: ゲート判定(3ゲート)をスキップして、Phase完了という重要な節目でDecisionLogger/LearningLoop/AgentMemoryからシグナルを収集し、VerifiedFactsを更新する。
